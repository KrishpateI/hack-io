# Data sources

Every dataset SafePath uses, with origin, license position, retrieval date, counts and limits. All retrieval dates
below are from the repository's own records (`data/processed/summary_report.json`, `data/processed/fallbacks.json`,
`data/sources/catalog.json`). SafePath is an experimental prototype with no official standing; none of these sources
endorses it. The same records are served at runtime by `GET /api/sources` and shown in the app's Data Sources screen.

### OpenStreetMap attribution (ODbL)

OSM data feeds the street merge, the pedestrian paths, the buildings layer and the basemap. The map shows
"© OpenStreetMap contributors" (link: https://www.openstreetmap.org/copyright) without user interaction, and the source
records for OSM datasets carry the license and attribution requirement. The processed graph is a derived database
of ODbL data; anyone redistributing it needs to keep the ODbL attribution and share-alike terms. Raw files
(`data/raw/*`), the intermediate downloads (`data/processed/osm_*/`, `cdp_centerlines/`) and the merged segments
(`data/processed/streets/`) are git-ignored. The graph artifact under `data/processed/graphs/` (about 21 MB, including the
13 MB buildings layer) and the PMTiles file are not ignored, so they can be committed; `scripts/check_large_files.py`
rejects any file over 50 MB.

### Fallbacks recorded for the datasets

Each dataset has a fetch policy of 3 attempts of 60 s each, then the previous raw copy, else the dataset is recorded as
missing in `data/processed/fallbacks.json`. In the run of 2026-10-24 every download was "freshly downloaded" with no
errors. If a street download fails the graph build has nothing real to use, and the app falls back to the SIMULATED
fixture graph (reported by `/api/health` and `/api/graph/status`).

## Street segments: source precedence (`scripts/process_streets.py`)

Inputs: Chicago Data Portal (CDP) street centerlines, OSM streets, OSM pedestrian paths (all from
`scripts/download_chicago_data.py`). Output: `data/processed/streets/segments.jsonl.gz` (git-ignored)
and a `street_processing` section in `data/processed/summary_report.json`.

Reproduce:

```powershell
backend\.venv\Scripts\python.exe scripts\download_chicago_data.py
backend\.venv\Scripts\python.exe scripts\process_streets.py
```

| Attribute | Retained source |
| --- | --- |
| Geometry, street name | CDP when a CDP segment exists, else OSM |
| Road class | OSM `highway` when matched or OSM-only; CDP-only keeps `cdp_class_<code>` |
| One-way | OSM; CDP `dir_travel` only when OSM states nothing |
| Pedestrian access, bridge, tunnel, layer, wheelchair | OSM only (CDP has none of these) |
| River crossing | CDP river lines (class `RIV`); otherwise `Unknown` |

Matching: a CDP segment is paired with the OSM way that overlaps it most (12 m buffer, same normalized
street name needs 60 % overlap, a different or missing name needs 90 %). Unmatched segments from
either source are kept with that single source. Name or one-way disagreements keep the source above
and record a conflict on the segment (`conflicts`, `attribute_sources`) and a warning in the summary.

Rules: absent attributes are the string `Unknown` and are never defaulted. `infrastructure_level` is
only assigned where a source says so (bridge, tunnel, viaduct as elevated, negative layer as
lower-level, explicit layer 0 or explicit `bridge=no`/`tunnel=no` as surface). Pedestrian paths are
walking segments; `highway=steps` is wheelchair inaccessible, other paths stay `Unknown` unless
tagged. Streets list `walking` only when OSM states foot access.

Known limits: CDP `tiered` and z-level fields are not used to infer levels; CDP names with suffixes
such as `OB`/`IB` can raise name conflicts against OSM; wheelchair data is sparse in OSM.

## Elevation: USGS 3DEP (`scripts/import_elevation.py`)

Samples the USGS National Map 3DEPElevation ImageServer (`getSamples`, batched multipoint, WGS84) at every
unique segment endpoint from `data/processed/streets/segments.jsonl.gz`. Values are meters, vertical datum
NAVD 88, each with its source cell size. Outputs: `data/processed/elevation/node_elevations.jsonl.gz`, an
`elevation` section in `data/processed/summary_report.json` (node, known and Unknown counts, edge confidence
counts, p5/p95 percentiles for the flood module), and `elevation:`-prefixed warnings in
`data/processed/fallbacks.json` (other keys are preserved). The request cache `data/raw/elevation/cache.json`
is git-ignored (`data/raw/*`); re-running resumes from it.

Reproduce:

```powershell
backend\.venv\Scripts\python.exe scripts\import_elevation.py
```

Rules: a point with no data, a sentinel value or a failed request is `Unknown`, never zero and never
interpolated. Failed requests are not cached. Three consecutive failed batches or the runtime cap stop
sampling; remaining points stay `Unknown` and `elevation:partial_coverage` (or `elevation:3dep_unreachable`
when nothing was sampled) is recorded. Each edge gets `elevation_start`, `elevation_end` and
`elevation_confidence`: `Unknown` if either end is Unknown, `Low` for bridge, tunnel, elevated, lower-level or
underground edges, `High` for explicit surface edges with both samples from 1 m or finer data, else `Medium`.

Limitation: 3DEP is bare-earth terrain. It does not describe bridge decks, tunnels or underground levels, so
terrain elevation on those edges can be far from the traveled surface (hence Low confidence), and higher
terrain does not guarantee flood safety.

## Basemap tiles: Chicago PMTiles extract (task 14.3, Req 41.1, 3.8, design D8)

Source: the Protomaps Basemap daily planet build (vector tiles derived from OpenStreetMap, ODbL Produced Work,
about 139 GB, zoom 0 to 15), URL pattern `https://build.protomaps.com/YYYYMMDD.pmtiles`
(index: https://maps.protomaps.com/builds/, docs: https://docs.protomaps.com/basemaps/downloads). The bucket keeps
the past week of builds. Protomaps discourages hotlinking; we only read byte ranges once to build our own extract.
The `pmtiles extract` command fetches only the ranges for the box, so the planet file is never downloaded.

Tool: Protomaps `pmtiles` CLI (go-pmtiles) pinned to **v1.31.2** (released 2026-07-22). The script downloads
`go-pmtiles_1.31.2_Windows_x86_64.zip` from the GitHub release into `tools/bin/` (git-ignored) and verifies the
published SHA-256 (`a658baa4d7e55020aef6ca17bd9ff9faa1582671266b36f58c52db0ac8e785a1`; the arm64 digest is also
pinned in the script). No Python package replaces the CLI, so the CLI is used.

Reproduce:
```powershell
backend\.venv\Scripts\python.exe scripts\extract_pmtiles.py --dry-run        # prints the exact command, no writes
backend\.venv\Scripts\python.exe scripts\extract_pmtiles.py --download-cli   # real extraction
```
The command it runs (bbox order is lon,lat):
```
tools\bin\pmtiles.exe extract https://build.protomaps.com/<YYYYMMDD>.pmtiles data\processed\tiles\chicago.pmtiles --bbox=-87.68,41.85,-87.6,41.91 --minzoom=12 --maxzoom=16 --download-threads=4
```
Options: `--build-date YYYYMMDD`, `--source <url-or-local path>`, `--output`, `--minzoom/--maxzoom`, `--tools-dir`.
Without `--build-date` the newest build in the past 7 days is used.

Result of the run on 2026-10-24 (build 20261024): 26 range requests, 4.5 MB transferred, about 8.5 s, output
`data/processed/tiles/chicago.pmtiles` = 4,326,219 bytes (4.3 MB), `pmtiles verify` OK, tile type `mvt`, bounds
-87.68,41.85,-87.60,41.91, header zoom 12 to 15, 102 tiles. Because the file is far below 50 MB it is not
git-ignored (`scripts/check_large_files.py` passes); if a wider box or higher zoom ever exceeds 50 MB, add
`data/processed/tiles/*.pmtiles` to `.gitignore` and upload it instead of committing it.

Limitations:
- Protomaps vector tiles end at zoom 15. Zoom 16 is over-zoomed from the zoom 15 tiles by MapLibre, so no extra
  zoom 16 data exists in the file. The header maxzoom is 15.
- Zoom levels below 12 are not in the extract; the map shows the background colour only when zoomed out further.
- Set `VITE_PMTILES_KIND=vector`. The current frontend vector style draws only `water` and `roads` layers; richer
  styling (`@protomaps/basemaps`, glyph and sprite assets for labels) is a separate frontend task.
- Attribution: data is OpenStreetMap contributors under the ODbL. The map must show "© OpenStreetMap contributors"
  with a link to https://www.openstreetmap.org/copyright (the tile metadata already carries it).

Records written by the script: `data/sources/catalog.json` gets a `PROTOMAPS-BASEMAP-CHICAGO` entry (read-merge-write
keyed by `source_id`: organization, build date, zoom range, output size, ODbL attribution requirement) and
`data/processed/fallbacks.json` gets `tiles:chicago_basemap` (other keys preserved; only `tiles:` keys are replaced).

Fallback when extraction fails or the file is missing: the script exits 1 and records
`acquisition_status: unavailable` with the error. The app then uses light-use OSM raster tiles in development builds
only, or a blank basemap with no third-party tile requests in production. OSM tile servers
(tile.openstreetmap.org) are never bulk-prefetched; the service worker precaches only our own PMTiles ranges.

### Serving the file

Local development (Vite): copy the file into the frontend static folder and point the env var at it. Vite serves
`public/` with HTTP range support, which PMTiles needs.
```powershell
New-Item -ItemType Directory -Force frontend\public\tiles | Out-Null
Copy-Item data\processed\tiles\chicago.pmtiles frontend\public\tiles\chicago.pmtiles
# frontend\.env.local
VITE_PMTILES_URL=/tiles/chicago.pmtiles
VITE_PMTILES_KIND=vector
```
S3 and CloudFront: upload as a static object and use a same-origin or CDN URL.
```powershell
aws s3 cp data\processed\tiles\chicago.pmtiles s3://<site-bucket>/tiles/chicago.pmtiles --content-type application/octet-stream --cache-control "public, max-age=86400"
# frontend build: VITE_PMTILES_URL=/tiles/chicago.pmtiles (same CloudFront distribution) or https://<distribution>.cloudfront.net/tiles/chicago.pmtiles
```
Requirements for the distribution: forward and cache the `Range` request header (or use a cache policy that
does), allow `GET` and `HEAD`, return `206 Partial Content`, and if the file is served from a different origin set
CORS (`Access-Control-Allow-Origin`, `Access-Control-Allow-Headers: Range`, `Access-Control-Expose-Headers:
Content-Range, Content-Length, ETag`). Do not compress the object (PMTiles tiles are already gzip-compressed).

## CTA GTFS and transit alerts

`scripts/download_chicago_data.py` downloads the static GTFS zip and extracts GTFS parent stations that fall in the box:
38 stations, each with its routes and `wheelchair_boarding` (a value from the feed, or Unknown). They are written to
`data/processed/cta_gtfs/data.json` and published as the `cta_stations` layer in the graph artifact.

Limits: GTFS is a schedule. It says nothing about outages or entrance closures. A station's entrance safety status stays
Unknown unless an Official_Notice or an Officially_Verified report says otherwise. The Clark/Lake station model in the
graph is SIMULATED; only its coordinate comes from GTFS.

`GET /api/transit/alerts` is optional. It returns live CTA Customer Alerts only when credentials or the enable flag are
configured (`SAFEPATH_CTA_ALERTS_KEY` or `SAFEPATH_CTA_ALERTS_ENABLED`), with a 10 s timeout. On failure it returns the last cached alerts with their
original timestamp, or "live transit alerts unavailable". Alerts are route-level and are not evidence of station
entrance safety or physical accessibility. Live alerts were not exercised against the real CTA service from this machine's
test suite (tests use stand-ins).

## Elevation caveats (USGS 3DEP)

- 3DEP is a bare-earth terrain model in NAVD 88 meters. It does not describe bridge decks, tunnels or underground
  levels. An edge on infrastructure of that kind can have terrain elevation far from the surface people travel on, so
  those edges get Low elevation confidence.
- Result of the 2026-10-24 run: 51,604 segment endpoints sampled in 3 requests with 0 failed requests; 0 Unknown.
  Edge confidence on the 42,512 merged segments: High 18, Medium 38,534, Low 3,960. 5th and 95th percentile elevation:
  178.609 m and 185.277 m (a relief of about 6.7 m across the whole area, so elevation separates edges only weakly).
- During graph noding, 15,790 extra cut points were sampled; 15,690 were obtained, with 1 failed request. 102 graph nodes
  and 652 edges stayed Unknown, and are penalized as Unknown, never zero-filled.
- Source cell size is recorded with each value. "High" requires 1 m or finer data on both ends of an explicit surface
  edge.
- Higher terrain does not mean lower flood exposure. The flood module's wording is "lower modeled exposure".
- If 3DEP is unreachable, the script records `elevation:3dep_unreachable` or `elevation:partial_coverage` in
  `data/processed/fallbacks.json` and the affected nodes stay Unknown.

## The 2007 Central Business District plan (Historical)

Source: City of Chicago, Office of Emergency Management and Communications, "Central Business District Evacuation Plan",
dated 2007-05-16 (cover: "Additions 29 May 07"), 18 pages, retrieved 2026-10-24. It is classified **Historical** and
labeled "Historical reference (2007), not a current evacuation order" wherever it is shown. It is used only for planning
concepts. Its 87 records are marked `cbd_derived=true` and `active=false`; the Rules_Engine and the restriction
resolver exclude `cbd_derived` notices, so the plan can never act as an active Official_Notice, and it is never
evaluated against a live incident. Contact details and procedures in the 2007 text may be out of date.

Details: [cbd-plan-extraction.md](cbd-plan-extraction.md). Machine-readable excerpts: `data/sources/cbd_plan_2007.json`.

What was found (16 of 19 topics had extractable text):

- Evacuation Levels I, II and III with activation conditions (pages 4 to 7).
- Activation and evacuation authority (pages 3 and 8).
- Approximate CBD boundary in words: Division Street (north), Roosevelt Road (south), Halsted Street (west), Lake
  Michigan (east). No coordinates are given and none were inferred.
- Hot and cold zones, transportation coordination, road and expressway closure procedures, CTA and Metra coordination,
  Assembly and Transportation Centers (as a concept), temporary shelters (as a concept), communication procedures, and the
  roles of OEMC, CPD, CFD, CDOT and IDOT.

What was not found or not extracted:

- Criteria for shelter-in-place versus evacuation (the plan names shelter-in-place but gives no criteria).
- Specific Assembly and Transportation Center locations and specific temporary shelter locations.
- The per-agency participation matrices for Levels I to III (the dot columns are graphics and do not extract as text).
- Boundary geometry.
- The four appendices (CPD, OEMC, CTA and IDOT deployment plans) are not in the PDF. A search on 2026-10-24 did not
  locate them, nor any newer version of the plan. The search results are stored as `check_status: not_located` records
  in `data/sources/catalog.json`; their content is left unpopulated and nothing is inferred.

Storage: no copyright or reuse statement was found in the PDF or on chicago.gov, so redistribution permission is not
confirmed. The PDF is a git-ignored local cache (`data/raw/cbd_plan/`); only short attributed excerpts with page and
section heading are stored. `scripts/import_emergency_plan.py` regenerates the records.
